# Project housekeeping audit

Perform a full housekeeping pass over this project folder.

## Scope

Audit every file and folder EXCEPT the actual executable/source scripts.

Do not modify, refactor, reformat, or optimize:
- Main source files
- Script files
- Build/deploy scripts
- Any file explicitly marked as protected

You may inspect them for context, but do not change them.

In this repository:
- Protected (inspect only): `Chart Cue/*.lua`, `Segue/*.lua` (the scripts and their action scripts),
  `tools/*.ps1` (check, test, deploy, release, shots, ui-test, background), `.github/workflows/`, and
  `index.xml` (generated by the ReaPack workflow: never edit it by hand).
- In scope, but used by the tools: `tests/*.lua` (logic tests), `tools/ui-test.lua` (the UI test steps),
  `.luarc.json` (the Language Server settings of check.ps1). A change to them needs `.\tools\check.ps1`
  and `.\tools\test.ps1` (or the UI test) after it.
- Out of scope (report only, never change): anything outside the repository - the deployed copies in
  `%APPDATA%\REAPER\Scripts\`, Chart Cue's data folder `%APPDATA%\REAPER\Data\Chart Cue\`, the user's
  REAPER, and Claude's memory folder (CLAUDE.md).

## What to find

1. Deprecated files and folders
   - Old versions, backups, obsolete configs, superseded assets
   - Files no longer referenced by documentation, build steps, or the main workflow
   - Empty or near-empty folders

2. Duplicate or redundant content
   - Repeated documentation
   - Duplicate test files or near-identical tests
   - Redundant configs, examples, templates, or assets
   - Files that duplicate information already in README, CLAUDE.md, or another canonical doc

3. Useless or low-value tests
   - Tests that no longer test current behavior
   - Tests that duplicate other tests
   - Placeholder, skipped, commented-out, or meaningless tests
   - Tests referencing removed features, renamed files, or outdated APIs

4. Outdated instructions and documentation
   - README files, setup guides, usage docs, changelogs, CLAUDE.md, and comments in non-source files
   - Incorrect paths, commands, feature descriptions, version numbers, or workflow steps
   - Instructions that conflict with the current project structure
   - Missing instructions for important current workflows

5. Structural cleanup
   - Files in the wrong location
   - Inconsistent naming
   - Unclear folder organization
   - Documentation that should be merged, moved, renamed, or deleted

## Rules

- First inspect the repository structure and identify the project's current purpose, entry points, build/deploy workflow, and canonical documentation.
- Treat README.md and CLAUDE.md as primary sources of truth, but verify their claims against the actual files.
- Do not assume a file is unused solely because it is not mentioned in a README; check references, imports, build files, configs, and related assets first.
  Here, search for the file name (with Grep) in: `tools/*.ps1` (deploy, check, test, release copy or read
  files by pattern, for example "Chart Cue*.lua"), the `@provides` lines of the scripts, `.github/workflows/`,
  `.gitignore`, `.claude/skills/`, CLAUDE.md, PLAN.md and README.md.
- Separate tracked files (`git ls-files`) from local, git-ignored files (`release/`, `tests/result*.txt`,
  test logs): a git-ignored file is generated, not "unused". Report the 2 groups apart.
- For the documentation part, run the `help-sync` search (every text that names a feature, a tab, a Settings
  path or a file) instead of writing a new one.
- Do not delete or modify anything yet.
- Do not propose speculative refactors or new features.
- Keep the audit focused on cleanup, accuracy, duplication, and maintainability.

## Required output

The user does not read code: write the report in plain words (CLAUDE.md), with exact paths.

Return a concise audit report with these sections:

### 1. Project snapshot
Briefly state:
- What the project is
- Main entry points
- Build/deploy workflow
- Canonical documentation files
- Folders/files excluded from modification

### 2. Findings
For every issue, use this format:

- **Finding:** Short title
- **Type:** Deprecated / duplicate / useless test / outdated documentation / structural
- **Location:** Exact file or folder path
- **Evidence:** Why it is a problem, including references checked
- **Risk:** Low / medium / high
- **Recommended action:** Keep / update / merge / move / rename / delete
- **Proposed change:** Exact replacement text, new location, or deletion target

Sort findings by risk, highest first.

### 3. Documentation updates
List every README or documentation file that needs updating.

For each one, provide:
- Current problem
- Exact sections to change
- Ready-to-use replacement text where practical
- Whether the update is required or optional

### 4. Safe deletion candidates
List only items that are safe to delete after human review.

For each:
- Exact path
- Reason
- Evidence that it is unused or obsolete
- Any dependency or reference that must be checked first

### 5. Recommended action plan
Give a numbered, minimal action plan.

Separate it into:
1. Safe immediate cleanups
2. Documentation updates
3. Items requiring my decision
4. Items to leave alone

Do not execute any changes. Wait for my approval.

## After the approval

Make only the approved changes. A tracked file is deleted only after an explicit yes for that file (a "go" for
the plan is not enough: CLAUDE.md asks before anything is removed). Keep LF line endings (check for CRLF after
writing). Run `.\tools\check.ps1` and `.\tools\test.ps1` when a test or a tool reference changed. Report what
was done, in plain words. Commit and push only when the user asks; a commit with no change in the scripts is
not a new version (CLAUDE.md).
